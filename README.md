1. Мета лабораторної роботи

Експериментально дослідити повний цикл перетворення вихідного коду мовою C у виконуваний файл (Source Code → Preprocessor → Compiler → Assembler → Object File → Linker → ELF Executable → Loader / OS → Process Memory), навчитися діагностувати помилки лінкування, аналізувати структуру файлів формату ELF (.text, .rodata, .data, .bss) та дослідити розподіл адрес різних типів даних у віртуальному адресному просторі процесу (code, data, bss, heap, stack).

Головні питання лабораторної роботи:

- Як program.c перетворюється на executable?

- Де знаходяться код і різні типи даних програми?

3. Етапи збирання програми (Build Pipeline)

Завдання 1–3. Preprocessing, Compilation та Assembly (program.c)

1. Preprocessing (gcc -E program.c -o program.i):

   - Чому program.i значно більший за program.c? Замість одного рядка include <stdio.h> препроцесор вставив увесь вміст заголовного файлу stdio.h та всіх вкладених системних заголовків (понад 700–800 рядків оголошень типів і прототипів функцій).

   - Чи є program.i машинним кодом і чи може CPU його виконати? Ні, це все ще текстовий код мовою C з розгорнутими макросами та заголовками; процесор не може виконувати текстові файли.

2. Compilation (gcc -S -O0 -masm=intel program.i -o program.s):

   - Файл представлений текстовою мовою Assembly (синтаксис Intel) для архітектури x86-64. Це ще не machine code, проте в ньому вже чітко видно мітки функцій add: (з інструкцією add eax, edx) та main:.

3. Assembly (gcc -c program.s -o program.o):

   - Чому cat program.o виглядає зовсім інакше, ніж program.s? Бо program.o — це двійковий об'єктний файл формату ELF 64-bit LSB relocatable, який містить машинний код та службові таблиці, а не читабельний текст.

| File | Representation | 
| ----- | ----- | 
| program.c | Текстовий вихідний код мовою C із директивами препроцесора | 
| program.i | Текстовий код C після роботи препроцесора (без директив include, define) | 
| program.s | Текстовий код мовою Assembly (мнемоніки інструкцій процесора) | 
| program.o | Двійковий об'єктний файл (ELF relocatable), що містить machine code та таблицю символів | 

Завдання 4 та 5. Symbols та Linking (nm program.o, gcc program.o -o program)

За допомогою nm program.o виявлено символи:

- T main, T add — визначені безпосередньо у секції коду (.text) цього об'єктного файлу.

- D global_value — ініціалізована глобальна змінна (.data).

- B global_empty — неініціалізована глобальна змінна (.bss).

- U printf (Undefined) — зовнішній символ, реалізація якого відсутня у program.o.

Відповіді на питання:

1. Чи містить program.o реалізацію add() та main()? Так, обидві функції реалізовані в ньому (T).

2. Чи містить він реалізацію printf()? Ні, printf позначений як U (невизначений).

3. Як програма зможе використати printf()? На етапі Linking компонувальник (ld, викликаний через gcc) знаходить посилання на printf у стандартній бібліотеці C (libc.so.6) і зв'язує виклик у нашому коді з точкою входу бібліотечної функції.

Завдання 6. Діагностика та виправлення Linker Error (main.c + calculate.c)

- Помилка: При спробі зібрати виконуваний файл лише з main.o (gcc main.o -o app) виникає помилка:
  undefined reference to 'calculate'

- Чому compilation пройшла успішно, а linking — ні?
  На етапі компіляції (gcc -c main.c -o main.o) компілятору достатньо лише оголошення (прототипу) функції int calculate(int a, int b);, щоб перевірити правильність типів аргументів і сформувати інструкцію call. Проте на етапі лінкування компонувальник намагається знайти реальне тіло (реалізацію) символу calculate серед усіх переданих об'єктних файлів і бібліотек — і не знаходить його.

- Виправлення: Створення calculate.c, компіляція в calculate.o (gcc -c calculate.c -o calculate.o) та спільне лінкування обох об'єктних файлів (gcc main.o calculate.o -o app) вирішує невизначений символ і виводить очікуване 30.

4. Дослідження формату ELF та секцій пам'яті

Завдання 7. Заголовок ELF (readelf -h program)

| ELF property | Значення | 
| ----- | ----- | 
| Class | ELF64 | 
| Data | 2's complement, little endian | 
| Type | DYN (Position-Independent Executable file) | 
| Machine | Advanced Micro Devices X86-64 | 
| Entry point | 0x1060 (адреса _start, може трохи відрізнятися залежно від версії GCC) | 

Пояснення: ELF64 означає 64-бітний формат виконуваного та компонувального файлу Linux, а поле Machine підтверджує, що інструкції скомпільовані під 64-бітну архітектуру x86-64 (AMD64).

Завдання 8 та 9. Секції ELF (readelf -S, nm, objdump на program та sections)

| Section | Що містить (на прикладі наших програм) | 
| ----- | ----- | 
| .text | Виконуваний машинний код функцій (main, add, _start) | 
| .rodata | Дані лише для читання (Read-Only Data): рядкові літерали "Result: %d\n" та константа const char message[] = "Computer Systems" | 
| .data | Ініціалізовані глобальні та статичні змінні з ненульовим початковим значенням: global_value = 10, initialized = 123, static_initialized = 456 | 
| .bss | Неініціалізовані (або ініціалізовані нулем) глобальні та статичні змінні: global_empty, uninitialized, static_uninitialized | 

Завдання 10. Розмір областей executable та експеримент із .bss (size sections)

- До додавання масиву: bss займає близько 16 байтів, розмір файлу sections — ~16 KB.

- Після заміни на int large_array[100000];:

  - Секції text і data практично не змінилися, натомість секція bss зросла на 400 000 байтів ($100\,000 \times 4\text{ байти}$).

  - Розмір самого виконуваного файлу на диску (ls -lh sections) залишився майже незмінним (~16 KB).

- Чому файл на диску не виріс на 400 KB? Секція .bss (Block Started by Symbol) містить змінні, які при старті програми заповнюються нулями. Щоб не витрачати місце на диску для зберігання сотень тисяч нульових байтів, у заголовку ELF записується лише розмір цієї секції. Реальна фізична пам'ять виділяється й обнуляється операційною системою лише під час завантаження процесу в RAM.

Завдання 11 та 12. Dynamic Libraries (ldd program) та Process (process.c)

- Динамічні бібліотеки (ldd program): програма залежить від стандартної бібліотеки C — libc.so.6 (та динамічного завантажувача ld-linux-x86-64.so.2).

  1. Повна реалізація printf() не міститься всередині файлу program.

  2. Розширення .so означає Shared Object (динамічно розділювана бібліотека в Linux, аналог .dll у Windows).

  3. Операційна система завантажує код libc.so.6 у фізичну пам'ять один раз і відображає його сторінки (лише для читання) у віртуальний адресний простір усіх запущених програм.

  4. Це суттєво економить місце на диску та оперативну пам'ять, а також дозволяє оновлювати системні бібліотеки (наприклад, виправляти вразливості) без перекомпіляції всіх програм.

- Executable проти Process (process.c):

  - process на диску — це пасивний двійковий файл (набір інструкцій і даних у форматі ELF).

  - Після запуску ./process ядро ОС створює активний процес із власним ідентифікатором PID, виділеним віртуальним адресним простором, регістрами, стеком і станом виконання.

5. Дослідження адресного простору процесу

Завдання 13 та 14. Прогноз, розміщення змінних (memory.c) та ASLR

| Об’єкт | Очікувана область | Фактична область та спостереження | 
| ----- | ----- | ----- | 
| main | code (.text) | Найнижчі адреси (0x55... / 0x56...) — сегмент коду | 
| global_initialized | data (.data) | Одразу вище сегмента коду (0x55... + зміщення) | 
| static_initialized | data (.data) | Поруч із global_initialized (різниця 4 байти) | 
| global_uninitialized | bss (.bss) | Одразу після секції .data | 
| static_uninitialized | bss (.bss) | Поруч із global_uninitialized | 
| dynamic allocation | heap | Окрема область вище .bss (0x55... / 0x56... із великим відступом) | 
| local | stack | Найвищі адреси користувацького простору (0x7ff...) | 

Висновки з аналізу адрес та багаторазового запуску ./memory:

1. Глобальні та статичні змінні (як ініціалізовані, так і неініціалізовані) згруповані щільно одна біля одної в сегментах даних програми, неподалік від коду main.

2. Локальна змінна local (0x7ff...) та динамічна пам'ять malloc знаходяться дуже далеко від глобальних змінних і одна від одної — у різних кінцях віртуального адресного простору.

3. Вплив ASLR: При кожному новому запуску ./memory реальні адреси main, global_initialized, dynamic та local змінюються. Це результат роботи захисного механізму ОС — ASLR (Address Space Layout Randomization), який випадково зміщує базові адреси сегментів процесу при кожному запуску для захисту від атак переповнення буфера.

Завдання 15 та 16. Поведінка Stack (stack.c) та Heap (heap.c)

- Stack (stack.c): При вкладених викликах main → level1 → level2 → level3 адреси локальних змінних (&a, &b, &c) змінюються у бік зменшення (наприклад, ...e44 → ...e24 → ...e04, крок 32 байти на стековий кадр). Це повністю відповідає моделі стеку на архітектурі x86-64, де стек росте зверху вниз (від старших адрес до молодших).

- Heap (heap.c): При послідовних викликах malloc(sizeof(int)) адреси a, b, c розташовані в області купи зі збільшенням на фіксований крок (зазвичай 0x20 = 32 байти в реалізації glibc ptmalloc через службові заголовки чанків та вирівнювання до 16 байтів). Проте алокатор не зобов'язаний завжди видавати послідовні адреси — після звільнення (free) або фрагментації новий блок може бути виділений у вже звільненому місці.

6. Відповіді на контрольні питання

 1. Які основні етапи проходить C-програма до створення executable? Препроцесинг (Preprocessing), компіляція в асемблер (Compilation), асемблювання в об'єктний код (Assembly) та компонування (Linking).

 2. Що робить preprocessor? Обробляє директиви, що починаються з решітки: вставляє вміст файлів include, розгортає макроси define, видаляє коментарі та виконує умовну компіляцію (ifdef).

 3. Що створює compiler? Перекладає очищений код C у текстовий файл мовою Assembly для цільової архітектури процесора.

 4. Що робить assembler? Перетворює текстові мнемоніки Assembly у двійкові машинні інструкції та формує об'єктний файл (.o).

 5. Що містить object file? Скомпільований машинний код функцій, дані (.data, .rodata), таблицю символів (визначених і зовнішніх) та інформацію для релокації адрес.

 6. Навіщо потрібен linker? Об'єднує один або кілька об'єктних файлів та системних бібліотек у єдиний виконуваний файл, розв'язуючи всі посилання між символами та призначаючи фінальні віртуальні адреси.

 7. Що означає undefined reference? Помилку лінкування, коли в коді викликається функція або використовується глобальна змінна, оголошення якої було в заголовку, але її реалізація не знайдена в жодному з переданих .o файлів чи бібліотек.

 8. Що таке symbol? Іменована сутність в об'єктному або виконуваному файлі (функція або глобальна/статична змінна), яка має адресу та використовується компонувальником для зв'язування модулів.

 9. Чим header file відрізняється від library? Заголовний файл (.h) містить лише оголошення (прототипи функцій, макроси, типи) для етапу компіляції, а бібліотека (.a або .so) містить вже скомпільований машинний код реалізації для етапу лінкування.

10. Що таке ELF? Executable and Linkable Format — стандартний двійковий формат виконуваних файлів, об'єктного коду та розділюваних бібліотек в ОС Linux.

11. Що зазвичай містить .text? Скомпільовані машинні інструкції програми (код функцій), доступні лише для читання та виконання.

12. Що зазвичай містить .rodata? Незмінні дані (Read-Only Data): рядкові літерали та глобальні константи (const).

13. У чому різниця між .data та .bss? Секція .data зберігає глобальні та статичні змінні з початковим ненульовим значенням (вони фізично записані у файл), а .bss — неініціалізовані або нульові змінні, які не займають місця у файлі на диску.

14. Чому велика .bss не обов’язково означає такий самий приріст розміру executable? Бо .bss заповнюється нулями при запуску програми, тому у файлі ELF зберігається лише числове значення її розміру, а не самі нульові байти.

15. Що показує ldd? Список динамічних бібліотек (.so), від яких залежить виконуваний файл, та шляхи до них у системі.

16. Чим executable відрізняється від process? Executable — це статичний файл на диску з кодом і даними; process — це активний екземпляр програми в оперативній пам'яті, що виконується ядром ОС і має власний PID, стек, купу та стан регістрів.

17. Де концептуально розташовуються local variables? У стеку (Stack) у межах стекового кадру поточної викликаної функції.

18. Для чого використовується heap? Для динамічного виділення пам'яті під час виконання програми (malloc, calloc, realloc), розмір або час життя якої невідомі на етапі компіляції.

19. Яка різниця між stack та heap? Стек керується автоматично (LIFO) при виклику/поверненні функцій, працює дуже швидко, має обмежений розмір і росте вниз. Купою керує програміст вручну (malloc/free), вона значно більша за обсягом, але виділення пам'яті повільніше і можлива фрагментація.

20. Чому адреси можуть змінюватися між запусками програми? Через технологію безпеки ASLR (Address Space Layout Randomization), яка рандомізує розташування сегментів пам'яті процесу при кожному запуску.

21. Що таке temporal locality? Часова локальність — принцип, згідно з яким якщо програма звернулася до певної комірки пам'яті, з високою ймовірністю вона звернеться до цієї ж комірки знову найближчим часом (наприклад, лічильник циклу).

22. Що таке spatial locality? Просторова локальність — принцип, згідно з яким після звернення до певної адреси пам'яті програма з високою ймовірністю звернеться до сусідніх адрес (наприклад, послідовний прохід по елементах масиву).

7. Висновок

У ході лабораторної роботи було досліджено повний шлях побудови програми мовою C від вихідного тексту до виконуваного ELF-файлу (-E, -S, -c, компонування) та роботу з утилітами аналізу бінарних файлів (readelf, objdump, nm, size, ldd). Експериментально підтверджено поділ пам'яті на сегменти .text, .rodata, .data та .bss, доведено економію дискового простору завдяки секції .bss і динамічним бібліотекам (.so), а також на практиці встановлено розташування коду, глобальних змінних, купи (heap) та стеку (stack) у віртуальному адресному просторі процесу з урахуванням механізму ASLR.
